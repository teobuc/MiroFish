# 00 — Philosophy: What Actually Transfers

| | |
|---|---|
| **What transfers** | Procedure adherence, tool discipline, verification loops, output contracts, recovery patterns, context hygiene, cost discipline — everything a harness can enforce from outside the model. |
| **What doesn't** | Domain knowledge, reasoning ceiling, per-step correctness *p*, calibration, the long-horizon *p^n* floor — everything that lives in the weights. |

FABLE exists because of a viral tweet, and because the tweet was wrong in an
instructive way. This document is the argument for the whole framework. If you
read one doc, read this one.

---

## 1. The tweet, and why it cannot be true

The claim: you can "clone Fable-class behavior into Opus 4.8" by asking a
frontier model for its own "operating manual" — its system prompt, its habits,
its secret procedure — and pasting that into a smaller or older model.

This fails on two independent grounds.

### 1a. Models cannot reliably report their own machinery

The premise assumes a model has privileged, accurate access to how it works
and can write it down. The best available evidence says otherwise.

Anthropic's own introspection research ("Emergent introspective awareness in
large language models," 2025, https://transformer-circuits.pub/2025/introspection/index.html)
injected known concept representations directly into a model's activations and
asked the model whether it noticed. Even under these maximally favorable
conditions — the experimenters *knew* the ground truth and the injected signal
was strong — the best models detected the injection only about 20% of the
time. The rest of the time they either noticed nothing or, worse, produced
fluent, confident, *wrong* explanations. That is the key result: when
introspection fails, it fails by confabulating, not by going silent.

This is consistent with the older unfaithful-chain-of-thought literature.
Turpin et al., "Language Models Don't Always Say What They Think"
(NeurIPS 2023, https://arxiv.org/abs/2305.04388), showed that models produce
plausible step-by-step rationales that demonstrably do not reflect the actual
cause of their answers — bias the input and the answer flips while the stated
reasoning never mentions the bias.

So when you ask a frontier model "describe the operating manual that makes you
good at agentic work," you do not get its operating manual. You get a
well-written document *in the style of* an operating manual, generated by the
same next-token machinery as everything else, with no privileged access to the
weights. It reads authoritative because generating authoritative-sounding text
is precisely what these models are best at. It is confabulation with good
production values.

### 1b. Even a real manual would not transfer capability

Suppose, counterfactually, you obtained the genuine system prompt and
procedures of a frontier agent. Pasting them into a weaker model still would
not close the gap, because the gap is not procedural.

Gudibande et al., "The False Promise of Imitating Proprietary LLMs"
(2023, https://arxiv.org/abs/2305.15717) is the controlled version of this
experiment, run with vastly more transfer bandwidth than a prompt: they
fine-tuned open models on up to ~150 million tokens of frontier-model outputs.
The imitators learned the *style* — format, tone, confidence, hedging patterns
— well enough to fool human raters. On capability benchmarks they barely
moved, and on factuality they sometimes got worse, because they had learned to
sound right without being right. If 150M tokens of gradient descent on
frontier outputs transfers style but not capability, a fortiori a pasted
2,000-token prompt does not.

Capability lives in weights. A prompt can *route* capability that already
exists; it cannot install capability that doesn't.

## 2. Why the tweet felt true anyway

Three real effects made the demo videos convincing:

1. **Style transfer fools raters.** The Gudibande result cuts both ways: if
   imitation reliably fools human evaluators, then a model prompted with a
   frontier model's "manual" will *look* upgraded in any eyeball evaluation.
   Side-by-side vibes are exactly the evaluation this trick beats.
2. **Generic agent hygiene is a real, small bump.** The confabulated "manual"
   usually contains genuinely good advice — plan before acting, verify before
   claiming, keep tool outputs short — because that advice is all over the
   training data. Adding it to a lazy baseline prompt produces a real
   improvement. The improvement comes from the hygiene, not from anything
   Fable-specific.
3. **Nobody runs the A/B.** The honest comparison is three-armed: weak model
   bare, weak model + the "manual", strong model. Almost no one who shared the
   tweet ran arm three, or ran any arm more than once. FABLE ships
   `evals.gap_closure` (see §7) precisely so this comparison is one function
   call.

## 3. The salvage: harness engineering is real and large

Here is the honest version of the tweet, and it is worth building a framework
around: **most of what makes a frontier *agent* feel magical is not the model
— it is the harness.** Orchestration loops, verification gates, tool design,
context management, effort routing. That layer is ordinary software, it is
documented in public research, and it transfers completely, because you are
not asking the model to carry it. Selected results:

- **SWE-agent** (Yang et al., 2024, https://arxiv.org/abs/2405.15793): holding
  the model fixed and changing only the agent-computer interface — the tools,
  the output shaping, the feedback format — moved GPT-4's SWE-bench resolve
  rate from 3.8% (basic shell access) to 12.5%. A >3x gain from interface
  engineering alone, zero weight changes.
- **Medprompt** (Nori et al., 2023, https://arxiv.org/abs/2311.16452): a
  general-purpose model with a disciplined prompting-and-ensembling harness
  (dynamic few-shot, chain-of-thought, choice-shuffled self-consistency) beat
  Med-PaLM 2, a model *fine-tuned* for medicine, on MedQA. Harness beat
  specialist weights.
- **Anthropic's multi-agent research system**
  (https://www.anthropic.com/engineering/built-multi-agent-research-system): an
  orchestrator-plus-subagents harness outperformed a single-agent baseline by
  90.2% on internal research evals. The same write-up reports that roughly
  80% of the performance variance was explained by token spend — how much
  looking and checking the harness bought — not by prompt cleverness. Also the
  cost warning FABLE repeats everywhere: multi-agent runs burned ~15x the
  tokens of chat.

That is the product thesis. The tweet said "copy the soul." The truth is
"build the exoskeleton." The exoskeleton is buildable, testable, and honest
about what it does.

## 4. The two-column table

| Transfers (harness, this repo) | Does not transfer (weights) |
|---|---|
| **Procedure adherence** — the loop enforces plan/act/verify order; the model can't skip the gate because the gate is host code (`loop.py`, `verify.py`). | **Knowledge** — what the model knows about Kubernetes or Danish tax law is fixed at training time. |
| **Tool discipline** — schemas, `strict: true`, parallel-safe flags, capped and shaped results (`tools.py`). | **Reasoning ceiling** — how deep a chain of inference the model can hold. Effort dials spend more tokens on the ceiling it has; they don't raise it. |
| **Verification loops** — claim audits, fresh-process mechanical checks, adversarial refuters (`verify.py`). | **Per-step correctness *p*** — the probability a single step is right. No harness component touches it. |
| **Output contracts** — structured completion reports, digest limits, evidence citation requirements. | **Calibration** — whether the model's confidence tracks reality. A harness can *ignore* confidence (FABLE mostly does); it can't fix it. |
| **Recovery patterns** — typed failure exits, checkpoint/respawn, escalation ladders (`loop.py`, `memory.py`). | **The *p^n* floor** — see §5. Verification raises the chance a *run* succeeds; it cannot make individual steps more likely to be right. |
| **Context hygiene & cost discipline** — frozen prefixes, pressure ladders, effort routing, usage ledgers (`client.py`, `config.py`). | |

Every FABLE doc opens with a compressed version of this table. That is a
deliberate discipline, not a formatting tic.

## 5. The p^n argument: why the verification spine exists

If each step of a task succeeds independently with probability *p*, an
*n*-step task succeeds with probability *p^n*. At *p* = 0.95 a 20-step task
completes 36% of the time; at 50 steps, 8%. This is the arithmetic that makes
long-horizon agents feel flaky even when every individual response looks
smart.

The empirical version is stark. τ-bench (Yao et al., 2024,
https://arxiv.org/abs/2406.12045) measured frontier agents on realistic
tool-use tasks and reported pass@1 above 60% on retail tasks — but pass^8
(the same task succeeding on all 8 independent runs) below 25%. The agent
that works in your demo fails, on the same task, a coin-flip-ish fraction of
the time.

A harness attacks this from two directions, and it is critical to be honest
about which is which:

- It **cannot raise *p***. Per-step correctness is weights.
- It **can restructure the exponent**: catch failed steps at a gate and retry
  them (turning one *p^n* chain into *n* independent geometric trials),
  shorten chains via decomposition, and make failures cheap and typed instead
  of silent and compounding. This raises pass^k — reliability across repeated
  runs — which is the number production systems actually live on.

Hence the design: `end_turn` is a claim, not a completion; the gate decides
(docs/01-architecture.md §4); evidence, not narration, is the currency
(docs/04-verification.md).

## 6. The litmus test

FABLE's routing policy compresses to one sentence, quoted verbatim here
because it appears as executable code in `config.Router.route_step`:

> **If you can write an automated checker for a step, a scaffolded cheap model
> can probably do it; if you can only check it by being smart, you need the
> smart model.**

A step whose `verifier` is a shell command (`pytest -q`, `mypy .`,
`grep -c ...`) routes to the mid tier — verify-and-retry makes cheap safe,
because a wrong answer costs one retry, not a corrupted run. A step whose
verifier is the literal string `judgment` pins to the strong tier, because
there the checker *is* the intelligence, and you cannot buy that back with
retries. This is the whole cascade philosophy; docs/06-operations.md does the
cost arithmetic.

## 7. gap_closure: honesty as a checkable number

Every claim in this document reduces to one measurable quantity. Run the same
task suite three ways — weak model bare, weak model + FABLE, strong model —
and compute:

```
gap_closure = (scaffolded_weak − bare_weak) / (strong − bare_weak)
```

`evals.gap_closure` does exactly this (k ≥ 4 runs per arm, pass^k, per-task
flips). Our commitment, stated here so it can be held against us: **we publish
the number even when it is low.** A gap_closure of 0.30 on a reasoning-heavy
suite is not an embarrassment to be buried; it is the framework working as
described — it tells you precisely how much of that suite was harness-shaped
and how much was weights-shaped. The tweet's sin was not optimism; it was
unfalsifiability. FABLE's differentiator is that its honesty claims come with
a harness for checking them.

The same three-arm protocol is the core of `prompts/extraction.md` — the
honest replacement for "ask the model for its manual": observe a strong
model's *trajectories* (tool calls, orderings, checks — behavior, not
self-report), induce procedures from what it *does*, compile them into
checklists and gates, and A/B-verify on held-out tasks. Observable actions
only. Asking the model to describe its own process is named there as a banned
anti-pattern, with the ~20% introspection result as the citation.

## 8. Case study preview: MiroFish

This repo's host project is itself the argument in miniature. MiroFish's
agent code contains hand-rolled retry loops (four copies), a three-tier regex
parser for tool calls, and a `<think>`-tag stripper that reached one client
wrapper but not the raw clients. None of those problems are intelligence
problems; all of them are plumbing problems, and every one of them is solved
structurally by the harness layer FABLE provides (native tool_use deletes the
regex parser; one `FableClient` choke point means the normalizer exists
exactly once). The migration is three shims, detailed in
docs/06-operations.md §8. The reasoning MiroFish's agents do was never the
bottleneck. The plumbing was. That is the thesis, observed in the wild.
